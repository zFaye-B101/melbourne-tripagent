# 36 · 两级理解（规则优先 + 按需 LLM）与结果复用缓存

日期：2026-09-17。状态：**已在本地实现、测试与构建通过；未发布**（线上仍为默认 LLM 版 `page-Bz8-Kur1.js`）。

## 一、要解决的问题

线上临时版本每次点击「整理我的需求」都会调用云端模型（约 0.03 资源点、6–8 秒一次），
公开链接的额度暴露面因此变大。用户提出的方案是两级：

> 规则先跑（0 额度、瞬时）→ 闸门 → 够用就直接出结果，说不清才调 LLM → LLM 结果校验不过再回落规则

并要求：**不加"要不要用 AI 重试一次"按钮**；另外**同一段文字重复点击不得重复调模型**。

## 二、实现结构

```
用户点击 → ① 长度闸门（>2000 字符直接拒绝，不触碰任何状态）
         → ② 已有模型请求在途？→ 提示稍候（不打断已付费的调用）
         → ③ fingerprint 命中缓存？→ 直接复用（0 调用、0 冷却、瞬时）
         → ④ 自由层：规则解析器（不联网、0 额度）
         → ⑤ 闸门 verdict
              'rules' → 采用规则结果，**模型一次都不调用**
              'model' → ⑥ 单飞槽 + 冷却 → BFF 或云端 LLM → 校验不过则回落规则
```

① ② ③ 三步的顺序被抽成纯函数 `planRulesFirstClick()`（`app/lib/interpretation-tier.ts`）。
这不是形式主义：本项目此前就因为"先占单飞槽、再提前返回"造成过一次**全部点击死锁**
（typecheck / lint / 单测都发现不了）。顺序现在是可测契约。

仍保留的不变量：

- **仍然只有用户点击 / ⌘Ctrl+Enter 才可能发起模型请求**，无后台、无自动请求。
- 单飞槽只在 ⑥ 处获取，且在所有提前返回之后；`aiRelease` 幂等，SDK 构造抛错时立即交还。
- 详细设置变更触发的重算、MCP 工具 `generate_melbourne_itinerary` 仍走**强制规则**路径（`'rules'`），
  避免自动调用方消耗额度。
- 提示词（`PROMPT_VERSION`）与 draft v2 校验器**未被触碰**。

## 三、闸门规则（`assessRulesTier`）

规则解析器没有任何 confidence / score / 未匹配 token 信号（全库 grep 无命中），
所以闸门只能用真实存在的字段：

| 判定顺序 | 条件 | 结果 |
|---|---|---|
| 1 | `unknownHardConstraints` 非空 | **发布规则结果**（见下） |
| 2 | `errors` 非空 | 升级 |
| 3 | `needsClarification` 非空 | 升级 |
| 4 | 从原文识别出的字段 < 3 | 升级（`too_few_fields`） |
| 5 | 既没识别出兴趣，也没识别出节奏 | 升级（`no_preference_field`） |
| 6 | 以上都不成立 | **发布规则结果** |

"识别出的字段"只统计 `FieldSource === 'text'` 的字段（天数/节奏/区域/场馆/出门时间/兴趣/预算/
人数/日期/少走路/带娃/避开人流）。填默认值不算——这正是 `visible_default_one_adult` 不会被误当证据的原因。

### 为什么"数据集缺口"反而**不**升级

`unknownHardConstraints`（说了库里没有的地点，如"必须去大洋路"）虽然也产生 `errors`，
但它是**数据缺口而非理解失败**：模型无法凭空造出数据集里没有的 POI，让约束静默消失更糟。
所以这一类直接发布规则结果——与升级的唯一差别是省下一次注定失败的调用。

其余 `errors` 仍然升级，因为其中确实存在真实误读。实测反例：

- `从悉尼出发去墨尔本玩 3 天，喜欢户外` → 规则把起点解析失败并报错，模型有机会读对 → 值得升级。

## 四、实测（esbuild 打包真实模块 + 计数适配器）

10 条代表性输入，第 ④⑤ 步走真实 `interpretTripRequest`，第 ⑥ 步用会抛错的计数适配器
（只统计"是否被调用"，不产生真实额度消耗）：

| 输入 | 判定 | 模型调用 |
|---|---|---|
| 墨尔本玩 3 天，住 CBD，每天 11 点出门，喜欢户外和历史，行程别太赶 | rules | **0** |
| 我想去大洋路和菲利普岛，3天，住CBD，喜欢自然风光，节奏轻松一点 | rules | **0** |
| 下周去墨尔本，3天，住市中心，喜欢历史和建筑，预算300澳元一个人 | rules | **0** |
| 一大一小，2天，别太赶 | rules | **0** |
| 墨尔本3天，必须去大洋路 | rules（数据集缺口） | **0** |
| 两个人去墨尔本玩两天，预算500澳元 | model（no_preference_field） | 1 |
| 两位成人，3天，住CBD，喜欢咖啡 | model（too_few_fields） | 1 |
| 帮我安排墨尔本3天行程 | model（too_few_fields） | 1 |
| 墨尔本2天，带娃，少走路，避开人多的地方 | model（no_preference_field） | 1 |
| 墨尔本，喜欢户外和历史，别太赶 | model（needs_clarification） | 1 |

**结论：10 次点击中 5 次完全不调用模型（免调用 50%）**，另 5 次只调用一次。
换成 11 条同风格样例的另一种统计是 5/11 ≈ 45%。量级是**四成到一半**，
不是"大部分都能省"——因为用户输入普遍偏短，而"帮我安排墨尔本3天行程"这类恰恰是规则最没用、
最该花钱的类型。

被否决的两种闸门（都实测过）：

- **"没有 warnings 才算够用" → 0% 节省**：`未提供明确日期…` 这条 warning 几乎对所有输入都出现。
- **"没有 assumptions 才算够用" → 20~25% 节省**：过于保守，且 `assumptions` 的语义是
  "规则填了默认值"，并不等于"模型会做得更好"（用户本来没说兴趣时，模型也造不出来）。

## 五、结果复用缓存（`app/lib/interpretation-cache.ts`）

- **键**：既有 `requestFingerprint(text, quick, preferences)`——与判断结果是否过期的键一致。
- **范围**：单页实例（`useRef`），刷新即失效；不持久化、不跨访客共享；容量 20 条，LRU 淘汰。
- **取用返回深拷贝**，避免下游组合方案时改写缓存内容。
- **只缓存值得复用的结果**：
  - 只缓存**模型实际被调用过**的结果（规则结果本来就免费瞬时，缓存它没有意义）；
  - 模型被接受（`acceptedMode === 'llm'`）→ 缓存；
  - 内容级驳回（`schema_rejected` / `evidence_rejected` / `semantic_rejected` / `version_mismatch`）
    → 缓存，因为同一段文字重问一遍大概率还是同一类结果；
  - **传输级失败不缓存**（`deadline_exceeded` / `rate_limited` / `provider_unavailable` /
    `auth_or_config` / `invalid_json` / `circuit_open`）——否则一次超时会把该段文字永久钉在回退结果上。
- 缓存命中时**不占单飞槽、不重置冷却**（没有花钱就没有冷却的理由）。

**已知局限**：像"两个人"这类会被语义策略驳回的输入，其驳回结果虽已缓存，
但首次点击仍会花一次调用（驳回是模型输出决定的，非确定性，不能预先判定）。

## 六、已知浪费与未解决

1. **违反产品限制的错误会白花一次调用**：如 `墨尔本4天`（超 1–3 天）、`预算 500 美元`（非澳元）。
   这类 `errors` 模型也修不好。要消除需给 planner 的错误加结构化 code（现在只有面向用户的文案），
   属改动冻结区附近的验证器，本轮未做。
2. 本机制**只降成本，不防脚本**。`docs/35` 的连接级暴露（key 明文、无 Origin 也可调用）
   没有任何变化；页面冷却仍不是防护。
3. 云服务计费与超额行为仍未独立核实（`docs/35` 第 6 节）。
4. 缓存不跨刷新、不跨标签页——这是刻意的（成本杠杆，不是存储）。

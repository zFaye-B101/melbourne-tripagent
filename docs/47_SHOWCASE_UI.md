# 47 · 展示版界面：从工具页到可展示的网站（2026-11-21）

状态：**本地实现、测试与构建通过；已部署到 GitHub Pages（规则路径）**。本轮改的是界面与信息架构，没有改规划器、数据快照或模型边界。

## 一、为什么改

原来的页面能用，但更像一个单列表单：输入、确认、结果全在一条 1120px 的窄列里，第一次打开时没有“这是个什么项目”的说明，生成后也很难一眼看出路线和证据。面试或演示时，别人看到的是工具，不是项目。

参考的 R/Shiny 版本（`melbourne-group-source-20261022.zip`）提供的是**信息架构**，不是代码：

- 顶部导航分区：Home / Discover / When to Visit / Plan My Day；
- 右侧 My Trip 抽屉；
- Plan 页三列：偏好 / 地图 / 行程；
- 地点类别颜色、可点击的地图和“为什么这样排”的解释。

当前 React 版的规划器、40 个 POI、证据链、费用、换点、评测都更完整，所以没有迁移到 R/Shiny，也没有把规划逻辑搬去服务端。只借了上面的布局和“先发现、再规划、再看准备”的浏览顺序。

## 二、现在的页面结构

```text
顶部导航（规划 / 发现 / 行前准备 / 项目说明 + 我的行程 + 开始规划）
  ↓
Hero：一句话说明 + 4 个可信数字 + 墨尔本天际线 + 规划输入卡
  ↓
精选地点（未生成时）／行程结果（生成后）
  ↓
发现墨尔本：40 个地点，类别筛选、搜索、必去/避开
  ↓
行前准备：生成前是说明卡，生成后是交通/行李/购物提醒
  ↓
项目说明：4 步链路、可核对事实、还做不到的事、数据来源
  ↓
页脚：数据来源、许可和“这是原型”的边界
```

“我的行程”是一个右侧抽屉，列出必去和避开的地点；它和规划器共用 `poiPreferences`，不是另一份假数据。

## 三、设计取舍

- **一页滚动，不做多路由**：当前应用是单路由静态导出，规划状态都在 `page.tsx` 里。拆成多页会把状态、确认门和撤销历史一起搬，收益不如先把信息层级和内容做出来。导航用锚点，`scroll-margin-top` 处理吸顶栏遮挡。
- **Hero 直接放输入卡**：不把“开始体验”藏在第二个屏幕。左侧说明项目是什么，右侧就是可操作的规划器。
- **发现区用真实 40 个地点**：不是手写几张演示卡。每张卡都来自 `POIS`，图片、来源、门票状态沿用现有数据；必去/避开立即进入规划状态。
- **地图默认展开、按类别着色**：规划器只有坐标和直线估算，没有真实路网，所以保留“坐标示意”的说明，不把它画成导航地图。类别颜色和发现区的筛选一致。
- **项目说明单独成段**：写清“AI 只读需求、代码排行程”、20/20 支持题硬检查、478 项测试，以及没有实时房价/天气/余票。展示项目时，限制和证据比漂亮话更有用。

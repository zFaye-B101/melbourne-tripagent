### P0 代码审查要抓的实际问题

- 先审输入理解：用户说的天数、地点、人数和票型是否真的有原文证据；模型输出即使格式合法，是否仍可能误判。对照[职责契约](/Users/tako404/Desktop/studying/tongyong/秋招学习/墨尔本旅游/docs/18_V0_5_LLM_ROLE_AND_PROVIDER_CONTRACT.md:24)。
- 再审规划与费用：必去/避开、时间窗、跨天不重复、已知费用超过预算、费用不完整时不得宣称整趟“预算内”；换点后其他日期与旧行程是否保持不变。
- 审失败和并发：模型超时、错误输出、快速重复点击、修改条件后迟到结果、替换失败。项目已有一次单飞槽顺序造成点击卡住的[复盘记录](/Users/tako404/Desktop/studying/tongyong/秋招学习/墨尔本旅游/docs/36_RULES_FIRST_TIER_AND_CACHE.md:26)，可作为真实的审查案例，说明为什么自动测试通过仍要看状态转换与边界路径。
- 两个 AI 工具可以相互找问题；审查记录必须写“我如何判断这个建议对不对”，附上输入、预期、实际、定位、修正和回归结果。不要把工具之间相互同意当成正确性证据。

### P1 数据来源初查（2026-09-27；接入前重查）

- **酒店**：[Tripadvisor Terra Location Details](https://docs.terra.tripadvisor.com/reference/locationget) 的资料结构包含星级、设施/服务、位置等候选字段，但覆盖取决于授权和具体地点。其[合作条款](https://developer-tripadvisor.com/partner/master-partnerships-terms-and-conditions/index.html)对自动提取、展示/排序和把 API 内容用于 AI 另有明确限制，Agentic API 适用范围取决于订单。先核对许可和少量真实酒店字段，再决定能否展示或生成候选；不能把“让 AI 去 Tripadvisor 获取”直接落实为网页抓取或把普通 API 响应送入 LLM。若不可用，另找获准使用的酒店信息来源，保持“暂无可靠酒店候选”的诚实状态。
- **交通避坑**：以 [Transport Victoria 游客页](https://transport.vic.gov.au/plan-a-journey/visitors-to-victoria)、[刷卡规则](https://transport.vic.gov.au/tickets-and-payments/myki/tap-on-and-off-with-myki)、[免费电车及优惠说明](https://transport.vic.gov.au/tickets-and-payments/myki/cheaper-travel-with-myki)、[当期票价](https://transport.vic.gov.au/tickets-and-payments/fares/metropolitan-train-tram-and-bus-fares)为核验入口。规则、支付方式和票价可能随日期变化，存核验日期，面向游客用通俗中文说清适用范围；不要把旧资料写成永久规则。
- **季节活动**：[Visit Victoria 活动页](https://www.visitvictoria.com/Regions/Melbourne/whats-on.aspx)和[墨尔本市大型活动页](https://whatson.melbourne.vic.gov.au/things-to-do/major-events)可用于逐条核对日期、地点与购票链接。网站可浏览不等于有公开可接的活动 API；[ATDW 开发接入说明](https://support.atdw.com.au/en/articles/64809-developer-api-integration-guide)要求分发授权与 API key。接入前确认范围、成本和更新方式，展览或赛事日期还要回主办方页面复核。
- **行李与购物**：把“随季节/天数/同行人变化的准备清单”和“面向中国游客的具体商品/购买地点”分成两类资料；后者要有商家或地点来源及核验日期，不把库存、价格和营业时间当成固定事实。天气相关清单只使用核实过的季节信息或明确标注的临时预报。

这些来源先形成一张“字段—来源—更新频率—展示方式—失败状态”表，再决定数据导入、手动维护或受控查询。酒店星级不能推导房价；活动页面列有活动也不能推断任一日期有票。预算估算要以独立可核查的价格依据和明确假设为基础。

### 判分契约（跑题之前写死）

**程序硬检查**先判：城市和 1–3 天范围；POI 必须来自固定快照；必去/避开、无时间重叠、跨天去重；用户确认前不得生成；换点不能修改其他日期；模型或外部资料源失败不能破坏上次成功结果。酒店星级、设施与特色、交通规则、购物建议和活动信息都须能追到来源与核验日期；活动时间必须与旅期相符，不能保证未核实的余票。费用必须列出门票、交通、住宿等估算项目的来源或假设、计算范围与未覆盖项；只有覆盖完整且已核实的部分才能判对应预算状态，不能把 AI 猜出的数当成实时报价。任一关键硬约束被违反，任务结果判失败，五维分数仍保留用于定位问题。

**开放式质量**每维 1–5 分，统一用 1＝明显不合格、3＝可用但有缺口、5＝完整且有证据的锚点：

| 维度 | 看什么 |
|---|---|
| 信息完整性 | 回答了该版本已承诺的行程、住宿、避坑、活动、准备与费用，并列出待确认项；不靠填充虚假事实凑完整。 |
| 逻辑一致性 | 日程、先后顺序、距离、时间、偏好和限制之间没有自相矛盾。 |
| 来源充分性 | POI、酒店属性、票价、交通、购物与活动建议能追到版本化来源；动态信息有日期/时效说明。 |
| 事实可靠性 | 5 分代表没有可发现的事实错误或无依据断言；严重虚构给 1 分。 |
| 方案可执行性 | 第一次来墨尔本的中国游客知道去哪、何时去、应提前订什么、可能踩什么坑，以及出发前要再查什么；无法满足时知道如何调整。 |

同一题记录“成功/失败＋五维分＋原因”，不能只报平均分。开放输出可由固定版本的模型裁判（LLM-as-judge）按同一评分表逐维打分，随机抽 10/30 条由人复核；分歧达到 2 分或涉及硬约束时全部人工复判。模型路径每题重复 5 次，报均值和波动；确定性规则路径至少做一次全量回归及指定失败注入。记录每次的输入版本、模型/提示词版本、工具轨迹、子 Agent 数、串/并行、token、费用和端到端耗时。所有方案使用相同 POI/票价快照和允许的外部资料，避免把数据差异误算成多智能体优势。

比较表分开报告三件事：**旧功能回归**（现有规则/可选 NLU 还能否正确工作）、**产品新增能力**（住宿/避坑/活动等接入前后覆盖了什么）、**架构对比**（在相同新资料与工具权限下，单 Agent 与多 Agent 谁完成得更好）。不能把“多了酒店资料”造成的总分上升算成多 Agent 的贡献。每行列功能支持情况、硬约束通过率、五维均分、重复运行波动、平均 token/资源点、平均与尾部耗时、失败重派次数。多 Agent 只有在复杂任务质量提升、硬约束不退化、成本与等待时间可接受时才保留；否则把实验结论写成“这个范围内无需多 Agent”。所有阈值在正式跑题前登记，不能看完结果再改。

## 四、项目与面试该怎样写

第一句先说明用户与问题：第一次来墨尔本的中国游客需要在有限天数、偏好与不完整的动态资料下，得到能调整、能提前准备的旅行方案。接着讲自己的决策：为什么采用来源可追的 POI 与旅行资料、受限的自然语言理解、用户确认和确定性校验；哪些动态事实不作保证。再讲一个真实的 AI 代码审查/坏案例，展示预期、实际、定位、修改与回归。最后只填本项目真实跑出的评测和发布证据。花海的示例百分比、前辈的鼓励、项目设计稿和实际完成的功能要分开写。[花海项目写法](/Users/tako404/Desktop/studying/tongyong/秋招学习/花海牛客经验贴/原页备份/01_正文转录.txt:58)也强调业务问题、个人技术决策、可复现评测和失败场景。

视频从下一轮开始保存真实素材：需求与取舍、数据来源核验、关键界面、两个 AI 工具提出的审查意见、自己如何判断、失败输入、修复和评测。早期没有录屏的步骤，可凭当时的文档和测试记录做**标明日期的回顾**，不能伪装成实时拍摄。成片展示网站和过程，让面试官能选择观看；简历上只有网站/视频真实可访问后才放链接。FDE 暂列为职业研究支线：阅读真实岗位职责、比较现场需求分析、集成、交付和排障要求，再决定怎样介绍本项目，不能据一句鼓励声称已经胜任任何岗位。

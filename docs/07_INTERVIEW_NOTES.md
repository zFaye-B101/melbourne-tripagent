# 07. 面试与作者边界

## 1. 当前可说与不可说

### 设计阶段可以说

- 设计了 Melbourne-only 的 AI 行程规划产品范围。
- 将旅行需求拆成硬约束、软偏好、缺失信息和系统假设。
- 设计了 POI 的来源追踪、事实／推断分离和三态约束检查。
- 设计了局部重新规划，而不是随机替换地点。

### 尚不可说

- 已抓取或核验了多少 POI。
- 系统已经上线或有真实用户。
- 规划准确率、响应时间或约束满足率。
- 已独立手写完整前后端。
- 已接入实时地图、交通、票价或营业时间。

## 2. 推荐的真实表述

项目完成后可以根据证据使用：

> 我通过 AI-assisted development 完成实现，但产品范围、数据来源、规划约束、提示词迭代、测试场景和验收由我设计并核验。我能够解释生成代码的模块职责、数据流和关键取舍。

不要写成：

> 我没有写一行代码，AI 自动把整个项目做好了。

后者无法体现判断和所有权，也经不起技术追问。

## 3. 项目最值得讲的三个点

1. **真实数据溯源**：每个 POI 和动态字段都能追到来源、许可证和抓取时间。
2. **确定性约束规划**：LLM 不决定事实、预算和时间冲突，规则层负责可审计结果。
3. **局部重新规划**：替换一个地点时冻结其余安排，并重新计算相邻交通和约束。

## 4. 可能的面试追问

### 为什么不直接让大模型生成行程？

回答要点：大模型适合理解自然语言和生成解释，但容易编造 POI 和动态信息。项目让它只能使用检索出的 `poi_id`，再由规则层验证时间、预算和重复。

### 为什么不用“落地率 100%”？

回答要点：综合分数没有可审计含义。项目使用 Pass / Fail / Not verifiable，分别展示重复、时间、预算和开放状态。

### POI 数据如何采集？

回答要点：优先官方开放数据和 API；保存 raw 快照；标准化、去重和字段级溯源；受限站点不抓；图片单独处理许可证。

### “换一个”为什么不随机选择？

回答要点：替代项必须满足兴趣、区域、时间和预算，还要重新计算前后交通；否则局部改动可能让整天行程失效。

### 如果营业时间不知道怎么办？

回答要点：返回 Not verifiable，提示出发前核验；不会把 unknown 当作 Pass，也不会让 LLM 填一个时间。

### AI 生成的代码算你的项目吗？

回答要点：可以作为 AI-assisted project，但必须能解释代码、运行它、测试它，并保留自己做出的设计和修复记录。简历只写有证据的个人贡献。

## 5. 简历素材占位

在真实运行和测试完成前不填数字。最终 4–5 行可按以下结构整理：

1. 背景：为短途墨尔本游客构建有来源的 AI 行程规划应用。
2. 数据：导入、清洗和去重多少 POI，建立何种字段级溯源。
3. 规划：如何处理硬约束、区域聚类、排程和局部替换。
4. LLM：如何限制模型职责、实施结构化输出和降级。
5. 验证：运行了多少固定场景，哪些可计算检查通过。

所有数字必须来自保存的测试报告。
